# Open Apple CVEs
These are CVEs which cannot be patched but nonetheless need to be filed and known.  To this day Apple has not issued CVEs about these problems (they are arbiters of CVEs on their platform).  We now need to issue CVEs outside of Apple’s authority and note their reluctance to issue CVEs against any security issue they cannot patch, a dangerous precedent.

# The USB-PD VDMs Allow a Device in Restore to be Reset or Forced to DFU

Because of the ability of a macOS devices with the USB-C port known as the ACE to issue VDMs (Vendor Defined Messages) and these VDMs can both reset an attached devices as well as force them into DFU mode (prior art, t8012 team as well as `macvdmtool`) a technician workstation which is malicious can reset an attached device that is being “restored” instead of actually restoring the device.  This is most obvious when the device is being reset from “recovery” mode and not “DFU” mode as recovery mode will cause the device to fail and re-enter recovery.  This is also secondarily difficult because a malicious power adapter can still push a device to DFU and run `checkra1n` - this was publicly announced last year as `Plug``'``nPwn`

# For the T2 and other iDevices, Capture of an APTicket Allows Downgrade to that Version

Because of the DFU bug known as `checkm8` a device which has a APTicket saved by an attacker can be forced down into the same version from which the APTicket was captured.  This is because the APTicket’s APNonce is only valid in the context of a recovery and restore path, which are not valid given ACE in DFU.  This is most disturbing on T2 logic boards before bridgeOS 5.0 where the T2 gained Signed System Volumes that ensure that the root filesystem is valid.  The only known countermeasure is to have the T2 / logic-board replaced with a version which has never had an APTicket for down versions issued for that ECID and older versions of bridgeOS.  This applies to any other `checkm8` vulnerable version of XNU.

# The Update Partition Allows for Circumvention of Signed System Volumes

Because a deice booted with `boot-command=update` will boot from the update partition (which has SIP disabled as a necessitate part of it’s job) it allows any bug in a prior version of XNU or “update brain” to be leveraged as a root-kit.  The problem here is that Apple’s implementation of iBoot fails to show a visual indicator that a device is being booted into an upgrade, recovery or unsigned environment.  This is most reverent to the M1 which this is still applicable.  The boot screen must show indications if the device is not booting a secure normal mode to be able to prevent this form of attack.  I am already working on detection using out-of-band measurement using `libimobiledevice` to read of NVRAM from a high integrity environment.  The M1 can also be restored to health by having the device restored at the Apple store and ensuring you have a new administrative password that is not known to an attacker.

# The `SysCfg` of a `checkm8` Device May Be Overwritten

Because `checkm8` is so early, the SysCfg storage can be overwritten with a new serial number or more disturbingly a value called `MoPED` which seems related to forced DEP enrollment.  Because APTicket doesn’t include a hash of the expected value of SysCfg it is impossible to detect modifications to this region.  The device integrity can generally still be asserted by pushing the device to DFU and reading off the ECID from a valid technician workstation.  This is in fact how the SNR (serial number reader) is able to verify AppleCare of a device where the serial number cannot be read from the Settings app.  Apple should implement universal SNR checks of any device brought in to an Apple store, as well as use the SNR to push the device to DFU instead of attempting the key chord and using iTunes / Finder for recovery for a user.  A clone of the SNR cable’s capabilities of DFU and reset is in the works to bring this high-integrity recovery process to private citizens and corporations.

# Apple Does not Display Pairing Relationships in the Settings App

To this day, especially after the iOS 5 juice jacking issues, Apple has not implemented a single simple countermeasure, to display the existing paring relationships in the Settings app.  This is a simple design change that requires almost no work on Apple’s part but has massive security impact.  Moreover, unlike Android; Apple conflates a “paired device” with a device which can be debugged.  This is because of Android’s history of not having “pairing relationships” with an App like iTunes.  Apple could enhance this model by having “pairing records” with the second step of enabling “debugging” after such a relationship.  Because most users would use the former without the later the former is a clear escalation of privilege.  At the very least you should be able to see and delete paring relationships with the Settings app.  If Apple is actually serious about the non-use of personal devices for debugging, then any device which has debug enabled should show this in the boot screen to indicate this has been allowed for the device.  This is an example of how a minimalistic design has actually failed to show users important information about the security of their device.

# Apple Doesn’t Provide an Audit Trail

The iCloud services expect that a malicious actor cannot also delete any email such as “signed in on a new device”.  Services like Microsoft and Goole show a history of account access on the website so that even if emails are deleted that a user would still know a security related event occurred. This is compounded by the fact Apple doesn’t even try emailing a user when a iCloud backup is restored, which often can include login information for Apps.
